# RW007 固件能力与遥控、ECHO 限制

记录日期：2026-10-01。适用硬件为本工程的 HMI-Board V3.1，实测模块固件为 `RW007_2.1.0-a7a0d089-57`。

## 主控能控制什么

RA6M3 运行本工程的代码，RW007 运行模块内部的独立固件。主控通过 SPI 命令请求模块扫描、连接、广播或收发协议支持的数据。

我们可以修改 RA6M3 的程序、调用和组合模块公开的功能；但修改 `ble.c`、增加宏或添加一个例程，不会改变 RW007 固件内部的 GATT 服务和数据处理逻辑。本次获取的是官方主控侧驱动源码，没有取得可用于修改、构建模块固件的完整工程和工具链。

因此“只能用”应理解为：当前工程只能调用已开放的接口。若厂商提供新固件及配套协议，或提供可开发的模块固件 SDK，能力可能扩展；本次没有刷写模块固件，也未验证任何替代固件。

## 当前固件的用途

| 功能 | 官方接口或说明 | 本工程验证情况 |
| --- | --- | --- |
| Wi-Fi 扫描、连接路由器、SoftAP、网络数据收发 | 官方 Wi-Fi 驱动提供 | 本轮未验证联网及网络收发 |
| BLE 辅助 Wi-Fi 配网 | 官方支持微信小程序配网 | 已开启对应广播；未测试路由器凭据及完整配网 |
| BLE 被手机发现、连接 | 内置外围服务 | 用户已确认可扫描、连接 |
| BLE 主动扫描、连接其他设备 | 官方 BLE 主机接口提供 | 本轮未验证 |
| 按 UUID 读写远端特性、订阅远端通知 | 官方 GATT 客户端接口提供 | 本轮未验证 |
| 主控自定义本地 GATT 服务 | 当前公开协议中未找到相应接口 | 未实现 |
| 手机任意写入转交主控、主控任意回复手机 | 当前公开协议中未找到完整服务端接口 | 本次测试未观察到手机文本到达主控 |
| 经典蓝牙音频、A2DP、AVRCP | 当前公开驱动中未找到相应接口 | 未验证、未实现；不能仅由 BLE 可连接推断支持 |

典型用途是：手机通过 BLE 给模块配网，然后设备通过 Wi-Fi 与服务器通信。另一类用途是模块主动访问符合接口条件的 BLE 外设。具体应用仍需逐项验证。

官方 README 明确说明：“目前 RW007 的从机功能仅支持微信小程序配网使用。”`gattc_write_by_uuid` 是写入远端服务的客户端操作，不等同于从本地 FF02 向手机发送 indication。

## 手机看到的服务

用户提供的 UUID 前 8 位如下；尚未记录完整 128 位字符串，不自行补全剩余部分。

| 对象 | UUID 前 8 位 | 手机显示的属性 |
| --- | --- | --- |
| 服务 | `0000ffff` | 服务 |
| 特性 | `0000ff01` | write |
| 特性 | `0000ff02` | indicate |

本例程启用的是固件内置配网功能。这些属性表明手机可以与模块内部的服务交互，不代表它们构成 RA6M3 的串口 RX/TX。未找到对应模块端公开实现，不以 UUID 本身推断全部私有协议含义。

手机提示发送成功、模块内部处理写入、模块通过 SPI 转发给主控，以及主控向手机回复，是不同环节。当前测试只观察到手机提示成功，没有观察到主控收到测试文本。

## 诊断与实测

保留 `src/ble.c` 中的 `ble_probe` 命令，用于观察所有通过长度校验的非空 SPI 数据包。它分别统计总包数、BLE 包数、其他包数，以及包含连续明文 `HMI_PROBE1` 的包数。不把空 SPI 轮询算作收到手机数据。

复现步骤：

1. 编译烧录 `python scripts/build_flash.py`，当前仅启用 `INIT_APP_EXPORT(ble_start)`。
2. 用 `python scripts/monitor_msh.py --port COM8` 打开串口，在 MSH 执行 `ble_probe` 和 `ble_status`。
3. 手机连接 RW007-ED30，订阅 FF02 的 indication，向 FF01 以文本方式发送 `HMI_PROBE1`，不加换行。
4. 再次执行上述命令，对照接收统计与串口事件。

2026-10-01 实测：

- 诊断版编译 0 错误、6 个停用入口的未使用函数警告，Flash 94180 字节、静态 RAM 9704 字节；烧录成功，ELF 中仅有 BLE 例程初始化入口。
- 捕获连接事件 0xA3 和订阅事件 0xA8，说明模块事件可以通过 SPI 到达主控。
- 订阅及一次广播命令应答后，01:08:30 和用户反馈后 01:09:08 均为 `packets=9 ble=4 other=0 marker_packets=0`。
- 后一次 `ble_status` 为 `ready=1 adv_command_ok=1 transfers=1052 errors=1`，通信继续运行；唯一错误是启动首包重试，期间未增加。
- 用户反馈发送成功，未看到回复；主控没有收到新的数据包或测试文本。诊断版自身没有回显实现，不能单凭“手机未收到回复”判定收发能力。
- 本地日志：`logs/msh_20261001_010631.log`。诊断仅检测单个包内连续明文，未穷举私有编码、分片或未公开协议。

## 对后续例程的处理

`ble-remote.c` 和 `ble-uart.c` 所需的两条通路是：手机写入交给 RA6M3，RA6M3 的回复交给手机。结合官方外围功能说明、公开接口缺失和此次实测，当前固件的已公开路径不足以实现这两个例程。

用户已要求将限制归档。本轮暂缓这两项功能，不创建仅有本地变量或串口输出的占位例程，也不标记为功能验收通过。保留唯一运行例程 `ble.c` 及已实测的诊断命令。

恢复开发的条件之一是取得厂商提供的通用 BLE 收发固件及接口文档，或使用具备已开放 GATT 服务端/串口透传接口的模块。若更换模块，需要重新确认电气连接、传输协议和手机交互。

仅显示 Apple Music 播放信息涉及不同协议，不能直接用本次 FF01 测试推断不可行，另见后续媒体可行性说明。
